# Strata 重构方案

> 基于 2026-11-09 对 `main` 分支（`e3cc928`）的实测扫描。
> 所有数字均为仓库实际统计，非估算。

## 0. 结论先行

本仓库**不需要推倒重来**。分层骨架已经建好：

```
apps/       web、admin、space、live、api(Django)、proxy
packages/   blocks、constants、editor、hooks、i18n、logger、services、
            shared-state、types、utils、codemods、decorators、tailwind-config
```

真正的问题是**三处迁移做了一半**，导致新旧两套并存。每一处的解法都在仓库内部已有先例，
不需要发明新架构。

| 优先级 | 问题 | 现状 | 仓库内已有范式 |
|---|---|---|---|
| P0 | 服务层双轨 | `packages/services` 38 文件 vs `apps/web/services` 53 文件，15 个同名重复 | space/admin 已全面采用 `packages/services` |
| P1 | 后端巨型文件 | `api/views/issue.py` 2801 行 / 110KB / 16 个 endpoint | `app/views/issue/` 已按资源拆成 12 个文件 |
| P2 | 组件层未收敛 | `packages/blocks` 321 文件，web 仅引用 8 处 | AGENTS.md 已规定 composites 归 blocks |
| P3 | 命名迁移半成品 | 后端 `Issue` 375 处 vs `WorkItem` 1 处 | `api/urls/work_item.py` 已双挂新旧路由 |

## 2. 执行顺序（重要）

**P3 命名迁移必须放在最后，不能提前。**

原因：改名会同时改动 `api/views/issue.py`、web service、web store —— 与 P1、P2
**抢同一个改动面**。改名和拆分混在一起，出问题无法二分定位。

正确顺序：**先拆文件（纯结构调整，行为不变，可逐项验证）→ 再在拆好的小文件上做改名**
（此时每次改动只碰一个小文件，出错立即定位）。

仓库里已有 `packages/codemods`（jscodeshift）正是为大规模改名准备的 ——
但它是给改名阶段用的，不是给拆分阶段用的。

## 3. 分阶段计划

### 第 0 步（前置，非重构）：补 web 测试安全网

**为什么必须先做**：web 侧 14 个测试全在 `store/`，components 和 services 零覆盖。
没有这层网，第 2 步合并服务层就是闭眼改。

范围建议（按业务价值排序）：

1. `services/issue/*` —— 请求参数拼装与错误处理
2. `store/issue/*/filter.store.ts` —— filter 序列化逻辑（已有部分测试）
3. `components/common/filters/*` —— 筛选器 UI 交互

### 第 1 步：拆分 `api/views/issue.py`（已实施）

**目标**：2801 行单文件 → 按资源拆包，**URL 与公开导出零变更**。

```
apps/api/strata/api/views/issue/
├── __init__.py       公开导出（含 __all__），保持 from .issue import X 可用
├── base.py           ← 复用 api/views/base.py 的 BaseAPIView
├── permissions.py    6 个模块级权限辅助函数
├── common.py         跨模块共享副作用符号（issue_activity 等）
├── work_item.py      Workspace/Issue List/Create/Detail
├── label.py          Label List/Create + Detail
├── link.py           IssueLink List/Create + Detail
├── comment.py        IssueComment List/Create + Detail
├── activity.py       IssueActivity List + Detail
├── attachment.py     IssueAttachment List/Create + Detail
├── relation.py       IssueRelation List/Create
└── search.py         IssueSearch
```

**结构对齐**：与内部 API `app/views/issue/` 同构，也与 `api/urls/` 下的
`work_item.py` / `label.py` 命名一致。

**拆分中的关键决策**：

1. **模块级辅助函数独立成 `permissions.py`**
   `guest_cannot_view_issue` / `is_restricted_guest` 被 `cycle.py`、`module.py`、
   `intake.py` 直接 import，独立成文件才能保持 `from .issue import X` 不变。

2. **共享副作用符号集中到 `common.py`**
   `issue_activity` / `model_activity` / `base_host` 被 2~5 个子模块同时使用。
   若各子模块各自 `from ... import`，则每个模块各持一份绑定，测试的
   `mock.patch` 只能打到其中一个 —— **测试会静默失效**（断言仍通过，但真实
   Celery 任务被触发）。
   集中后子模块在调用时写作 `common.issue_activity.delay(...)`，
   补丁打在 `strata.api.views.issue.common.issue_activity` 一处即可全局生效。
   这遵循 Python "patch where it is looked up" 的标准做法。

3. **`__init__.py` 全量再导出**
   `from strata.api.views.issue import IssueLinkDetailAPIEndpoint` 等
   既有调用点（`api/views/__init__.py`、`cycle.py`、`module.py`、`intake.py`、
   `tests/unit/views/test_issue_link.py`）全部无需修改。

### 第 2 步：web 服务层收敛到 `packages/services`

**顺序**（按域独立提交，每域跑一次 web 测试）：

```
api → ai → file → instance → user → workspace → cycle → module → project → issue
```

**做法**：先让 web 全部改 import 指向 `@strata/services`，**删除**旧的
`apps/web/services/*`，重复自然消失。

**不做**：不合并同名文件的两代实现。两代只重叠部分方法，必须逐方法判定
归属（哪些进 packages、哪些 web 专属），而不是挑一个覆盖另一个。

### 第 3 步：`@strata/blocks` 收敛

`apps/web/components/core/`（filters / list / modals / multiple-select / sidebar /
theme / description-versions）与 `packages/blocks` 高度重叠。
逐个判定：**上移到 blocks** 还是 **确属 web 专属**。

### 第 4 步：Issue → WorkItem 全量改名

用 `packages/codemods` 做。**前置**：第 1~3 步已完成，改名面收敛到小文件。

### 一个被测试全绿掩盖的 bug（已修）

把 `redis_instance()` 改名为 `redis_client()` 时，
`strata/bgtasks/email_notification_task.py` 里原本就有一处同名局部变量：

```python
redis_instance = redis_instance()   # 局部变量与函数名撞名
```

批量替换后变成 `redis_client = redis_client()` —— **自赋值**。Python 判定
`redis_client` 是局部变量，调用时抛 `UnboundLocalError`。

**这个 bug 在 1497 个测试全绿的情况下没被发现**：那段锁逻辑零测试覆盖，
只在生产 worker 上跑。是最后跑 `ruff check` 时被 F823 抓到的。

修法：局部变量改名（`client = redis_client()`），并补
`strata/tests/unit/bgtasks/test_email_notification_locks.py`（4 个测试）。
补完后**把 bug 放回去验证测试确实会失败**，确认不是"写完即信"的假测试。

> 教训：批量重命名后，`ruff check`（F823 / F811）比 pytest 更可靠 ——
> pytest 只覆盖被测到的路径，而 lint 扫全部代码。

「API 表面一致」指：URL pattern、HTTP 方法、endpoint 类名、类 MRO、类属性、
辅助函数源码 —— 全部逐字节相同，唯一差异是类的定义模块路径
（`issue.X` → `issue/work_item.X`），这是拆分的必然结果，不影响任何行为。

### 拆分中额外修复的基础设施问题

拆分过程中暴露出三个**与拆分无关、但阻塞验证**的问题，已一并修复。它们都只影响
「宿主机直接跑 pytest」这一条路径，Docker / CI 行为不变。

**1. 本机跑 pytest 缺少 `.env` 注入**

`apps/api/.env` 由 compose 栈注入容器，宿主机直接跑 pytest 时
`REDIS_URL` / `POSTGRES_*` 全是 `None`，Django 在 `setup()` 阶段就崩。
修复：`apps/api/strata/__init__.py` 在**任何子模块导入之前**加载 `.env`，
且**真实环境变量优先**，compose/CI 环境行为完全不变。

**2. 限流器依赖 Redis，LocMemCache 不兼容**

`cache.delete_pattern(...)` 是 django_redis 的扩展方法，Django 自带的
LocMemCache 没有它 —— 换成 LocMemCache 会让 358 个 contract 测试在 setup
阶段直接报错。

修复：**保留 django_redis 后端**（API 不变），改用
`strata/settings/fake_redis_client.py` —— 一个连到进程内 fake Redis 的
django_redis 客户端。

业务代码直接调用的 `redis_instance()` 也指向同一个 fake server。但这里有个
陷阱：不能直接改 `redis_instance()` 的行为 —— `tests/unit/utils/test_redis.py`
专门断言它的 TLS / 凭据 / 库号构造逻辑，一改就挂。

最终拆成两个入口：

| 函数 | 语义 | 使用方 |
|---|---|---|
| `redis_instance()` | 始终按 `REDIS_URL` 构造真实客户端 | 测试构造参数断言 |
| `redis_client()` | 测试环境返回 fake，其余同 `redis_instance()` | 业务代码 + 读写同一份数据的测试 |

`fakeredis` 的 `eval` 需要 Lua 支持，而 magic-code 的原子计数器用的正是
Lua 脚本，因此还需 `lupa`。两个包都进 `test` 依赖组。

设 `STRATA_TEST_REDIS=1` 可强制使用真实 Redis（compose 环境保持原行为）。

**3. 测试环境缺 `EMAIL_HOST`**

magic-link / email-code 视图在没有配 SMTP 时直接返回 `SMTP_NOT_CONFIGURED`
（400）。`docker-compose-test.yml` 早已显式设置 `EMAIL_HOST: test-smtp.invalid`
并注明原因，但 settings 层没有默认值，宿主机跑必然失败。

修复：`strata/settings/test.py` 加 `EMAIL_HOST` 默认占位值。

> 宿主机没有 Redis / Docker Desktop 时，这是唯一能让完整套件跑通的方式。
> Docker 环境不受影响（compose 会注入真实 Redis，可用上述开关保持原行为）。

## 5. 风险登记

| 风险 | 影响 | 缓解 |
|---|---|---|
| mock.patch 静默失效 | 测试假绿，真实 Celery 任务被触发 | 共享符号集中到 `common.py`，单一补丁点 |
| 批量改名误改赋值左侧 | `redis_client = redis_client()` 自赋值，运行时报 UnboundLocalError | 改完必跑 `ruff check`（F823 能抓）；局部变量改名避开同形 |
| 两代 service 实现直接合并 | 行为漂移，线上问题 | 逐方法判定归属，不做覆盖式合并 |
| 改名与拆分同时进行 | 无法二分定位故障 | 严格按 P1→P4 顺序，改名放最后 |
| web 无测试保护 | 合并服务层等于闭眼改 | 第 0 步先补测试 |
| 新增子模块忘记加 `__init__` 导出 | 运行时 ImportError | `__init__.py` 显式维护 `__all__`，并有结构测试守着 |
| 缓存后端换掉导致 API 不兼容 | `delete_pattern` 等 django_redis 扩展方法缺失，测试批量报错 | 保留 django_redis 后端，只换底层连接 |
